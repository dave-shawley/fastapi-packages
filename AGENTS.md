# Agent guidance

This file is for agents first. Keep it minimal.

Do not copy repository facts here just because they exist elsewhere in the tree.
AGENTS files tend to be maintained mostly by agents, which makes them
vulnerable to silent bit rot. Agents SHOULD groom this file regularly, remove
stale guidance, and make AGENTS-only updates as a separate commit when needed.

## Repository boundaries

- Read `README.md` for repository structure and onboarding.
- Read `CONTEXT.md` before changing established domain vocabulary.
- Reusable, distributable packages live under `libraries/`.
- Tutorial and integration applications live under `tutorials/`; they are local
  development applications, not publishable library implementations.
- Keep application-owned authentication, dependency injection, and domain
  behavior out of reusable library dependencies.
- Preserve documented public APIs, entry points, state vocabulary, error
  contracts, and behavior unless the change is intentional and documented.

## Development environment

Use Python 3.14 for local development. Python 3.12 through 3.15 are supported
package runtimes and are tested by CI.

Required development tools include Python, uv, just, dprint, Docker Compose, and
OpenSSL. Run `just setup` after cloning or when the development environment
needs to be initialized.

Prefer the repository's `just` recipes for normal work. Recipes support
arguments for focused work; use `just --list` and the `justfile` for the
authoritative interface.

## Formatting, tests, and analysis

Always run formatting before tests:

```console
just format path/to/changed/files
just test [focused pytest arguments]
```

`just format` is intentionally first. It is faster than discovering formatting
failures after another validation round and handles non-obvious details such as
import ordering. Do not guess how code should be formatted.

For implementation changes:

1. Run `just format` on the relevant files.
2. Run focused tests, then broaden tests when the change crosses package or
   application boundaries.
3. Run `just analyze` on the relevant files.
4. Run `git diff --check`.
5. Preserve the repository's 100% coverage threshold for tested code.

`just analyze` runs Ruff, Pyrefly, and dprint. Pyrefly checks the complete
repository context even when file arguments focus Ruff and dprint.

Use `just docs` after changing library documentation or documentation behavior.
Keep documentation synchronized with implementation, public behavior, and
`CONTEXT.md`.

If validation fails because of an environmental problem, report the exact
command and failure. Do not weaken code or repository configuration to hide
package-download, Docker, plugin, or other local-environment failures.

## Python and typing conventions

- Follow the configured Ruff, dprint, and Pyrefly rules.
- Prefer module-qualified imports when reasonable.
- Use single quotes and the configured line lengths; let `just format` decide
  formatting.
- Preserve strict typing and fix Pyrefly diagnostics rather than weakening
  annotations.
- Prefer `collections.abc` annotations when they express the required
  constraint, such as `collections.abc.Sequence[T]` or
  `collections.abc.Iterable[T]`, instead of requiring `list[T]` unnecessarily.
- Prefer supported public APIs over internal or undocumented APIs.
- Use explicit, validated principal identifiers for access logging. Never log
  credentials or infer identity fields when an explicit identifier is required.

## Dependencies and lockfiles

Use uv-supported commands for dependency changes. Never manually edit dependency
lists in member `pyproject.toml` files; use commands such as `uv add` and
`uv remove`.

The exception is the root `tool.uv.constraint-dependencies` section, which is
the intentional place for workspace-wide constraints and may be edited
directly.

Never hand-edit `uv.lock`. Identify whether a change belongs to the root
workspace lockfile or another application's separate lockfile, then use the
appropriate uv command. Review all uv-generated changes before committing.

## Runtime and generated state

Generated and local-only state must remain ignored and uncommitted, including:

- `runtime/`
- `build/`
- `dist/`
- generated documentation output
- local environment files
- private keys and tutorial credentials
- Docker-generated state and unrelated generated lock or build artifacts

Keys and runtime configuration generated by repository setup are exclusively for
the local tutorials. They MUST NEVER be used for production, staging, personal,
or external services.

## Documentation and vocabulary

Maintain documentation in the same topical change as implementation changes.
When a change affects a concept in `CONTEXT.md`, update the glossary and the
relevant documentation in the same commit.

Do not rename or redefine established concepts for stylistic reasons. Change
the vocabulary only when there is a concrete reason, then update source, tests,
documentation, imports, and logging configuration consistently.

## Git and commits

Inspect the worktree before staging:

```console
git status --short --branch
```

Commits MUST be topical. Each commit contains one coherent concern, including
its focused tests and required documentation. Do not mix dependency upgrades,
formatting-only changes, refactors, generated artifacts, or unrelated fixes
into one commit.

For each commit:

1. Inspect the current worktree and preserve unrelated changes.
2. Stage only the intended topic.
3. Inspect `git diff --cached`.
4. Run `git diff --cached --check`.
5. Commit the topic.
6. Reinspect the remaining worktree and the next topic.

Review files rewritten by formatters, Ruff, uv, or documentation tools and
restore the intended topical boundary before committing. Do not use destructive
Git commands to simplify staging or cleanup.

CI is authoritative for the complete supported Python matrix and packaging
workflow. Local validation provides fast feedback but does not necessarily
reproduce every CI environment.
